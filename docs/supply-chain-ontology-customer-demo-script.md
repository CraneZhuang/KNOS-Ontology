# 供应链本体客户演示稿

**主题：一个供应商出问题，如何看清影响，并找到应对方案？**

适用对象：采购、供应链、生产运营负责人，以及参与系统建设的信息化团队。  
建议时长：约 15 分钟，含点击、停顿和一次现场互动。  
主场景：当前系统中的「供应链中断与风险传播」。  
使用方法：正文可直接照读；每段的「屏幕操作」供演示者参考，不需要念给客户。文末附核心知识速查和问答。

## 一、开场：从一个真实工作中的问题开始｜约 1 分钟

**屏幕操作：**打开「供应链中断与风险传播」本体，保持完整图谱可见，必要时点击「适应视图」。

各位好，今天我们用一个大家容易遇到的情况，来看看本体能够为供应链管理提供什么帮助。

假设今天上午，采购同事收到一家关键供应商的通知：因为突发事件，接下来一周可能无法正常供货。

这时候，管理者通常会马上追问三件事：第一，这件事会影响我们的哪些产品？第二，现有库存还能支撑多久？第三，有没有可行的替代方案，谁来推进？

这些问题涉及采购、库存、生产和经营数据。很多时候，各部门都掌握了一部分信息，困难在于把这些信息按同一套业务含义接起来。

今天我们就围绕这三个问题，介绍本体的作用。当前页面展示的是业务模型，我们会用一个假设案例说明它如何组织分析；真实业务结果需要接入贵司的数据和规则后才能获得。

## 二、先理解本体：让系统认清业务对象及其关系｜约 2 分钟

**屏幕操作：**指向「本体统计」中的 7 个实体、7 条关系、40 个属性。点击图谱中的 `Supplier`；节点不方便点击时，也可从「搜索与筛选」结果中选择它。

大家可以把本体理解为：一套明确的业务定义，加上一张业务关系图。

我们先回答“业务里有哪些对象”。在这个场景中，有供应商、零部件、产品线，也有中断事件、风险评估、缓解措施和备选供应商，一共七类对象。

然后回答“每类对象需要记录什么”。例如供应商有名称、所在国家、供应链层级和历史交付评分；零部件有库存缓冲天数、补货提前期和关键程度。这些就是属性。

最后回答“对象之间怎样关联”。比如供应商供应零部件，零部件用于产品线。这些就是关系。

这里有一个容易混淆的地方：屏幕上的 Supplier 代表“供应商这一类业务对象”。真正某一家供应商的记录，是这个类型下的一个实例。我们现在先定义清楚对象的含义、需要的字段和连接方式，再让实际记录按这些约定组织起来。

请看 `supplierId`。它的作用，是让系统能够明确识别我们说的是哪一家供应商。如果采购系统和其他系统使用不同编码，接入时就需要建立对应关系。名称相似，不能直接当作同一家企业。

所以，本体建设的第一步，其实是业务人员和技术人员共同确认：我们说的每个对象，到底指什么。

## 三、沿着关系追溯：供应商出问题，为什么会影响产品线？｜约 2 分钟

**屏幕操作：**展开「路径查找」，起点选择 `DisruptionEvent`，终点选择 `ProductLine`，点击「查找路径」。页面应显示「最短路径 — 3 跳」。

现在回到刚才的问题：一家供应商停止供货，为什么会影响我们的产品？

我们从中断事件出发，把终点选为产品线。大家可以看到，系统展示了一条三步路径：

**中断事件影响供应商，供应商供应零部件，零部件用于产品线。**

这条路径把分析过程说清楚了。我们要判断某条产品线是否涉及此次事件，需要确认它使用的零部件，以及这些零部件与受影响供应商之间的供货关系。

再看零部件与产品线之间的关系。一个零部件可能被多条产品线共同使用，一条产品线也可能需要多个零部件，这就是多对多关系。

这个定义对业务很重要。我们不能只看某个零部件的采购金额，还要看它连接了多少关键业务。一颗金额不高的芯片，如果多条产品线都依赖它，也可能成为生产的关键约束。

路径展示的是模型中存在的连接。它帮助我们明确应该沿哪些关系查证；要判断具体哪些产品会受到多大影响，还需要实际供货、库存和生产数据。

我想请大家带着贵司的情况想一下：如果今天某家关键供应商停供，跨部门确认受影响范围，通常需要经过哪些人、哪些系统？这也是我们后续可以一起验证的一个起点。

## 四、从“有关联”走向“有风险”：库存和时间是关键｜约 2 分钟

**屏幕操作：**点击 `Component`，重点展示 `daysOfSupplyOnHand`、`leadTimeDays`、`criticalityLevel`；再点击 `DisruptionEvent`，展示 `estimatedDurationDays`。

看到关联之后，下一步要判断紧迫程度。

我们点开零部件。这里有三个值得关注的属性：库存缓冲天数、典型补货提前期，以及零部件的关键程度。中断事件上，还定义了预计持续时间。

这些属性让我们能把“供应商发生异常”进一步转化成业务判断所需的信息。

举一个纯粹用于说明的例子：假设某个关键零部件，在当前需求假设下，库存只能支撑三天，而供应中断预计持续七天。我们就需要优先核实：有没有可靠的在途到货，能不能调拨，替代来源何时能够补上。

三天和七天之间的差距，是一个需要调查的风险信号。实际是否停产、影响多少，还要结合库存是否已被占用、物料能否替代、生产计划和后续需求变化来判断。

在这里，本体的作用是把分析所需的业务事实定义清楚，让采购、仓储和生产讨论的是同一组对象、同一套时间和数量口径。

例如，“库存可用天数”采用什么需求预测，是否包含在途、是否扣除了已分配库存，都应该在接入真实业务时确认。这样，后续的分析结论才有一致的基础。

## 五、把评估本身变成可管理的业务对象｜约 1.5 分钟

**屏幕操作：**点击 `RiskAssessment`，展示 `assessedDate`、`revenueAtRisk`、`timeToImpactDays` 和 `confidenceLevel`。

现在看风险评估。

这里有一个很有价值的建模思路：我们把“评估”也作为一种业务对象。因为同一个事件，在不同时间、基于不同信息，可能得到不同结论。

例如，今天上午我们还不知道供应商何时恢复，下午收到了新的交付承诺，评估就可能发生变化。因此，需要记录什么时候评估、预计多久开始影响生产，以及对评估结果有多大把握。

这里还有 `revenueAtRisk`，表示预计受影响的收入。它需要由业务确认的计算逻辑产生，不能直接把相关产品线的全年收入都当成本次损失。评估周期、受影响订单、可恢复交付量等因素，都可能改变结果。

有了这样的结构，管理者可以围绕一组明确的问题讨论：这个判断依据什么信息？是什么时候做的？哪些地方还不确定？下一次应该补充什么信息？

这比只有一句“风险很高”，更便于沟通，也为后续记录依据和复盘提供了模型基础。

## 六、从风险走向应对：让措施和备选来源有清楚的含义｜约 2 分钟

**屏幕操作：**在「路径查找」中，将起点设为 `DisruptionEvent`、终点设为 `AlternativeSupplier`，点击「查找路径」。随后分别点击 `MitigationAction` 和 `AlternativeSupplier`。

接下来，我们再看另一条路径：中断事件触发风险评估，风险评估推荐缓解措施，缓解措施可以启用备选供应商。

这条路径表达的是应对过程中的业务关系。

缓解措施可以是启用备选供应商、加急运输、增加安全库存，也可以是调整生产或沟通客户。不同措施的适用条件、成本和时间效果各不相同。

我们点开备选供应商。这里定义了认证状态、可用产能和价格溢价。它们帮助我们提出更具体的问题：这个来源是否已经获批？可用产能能不能满足需求？额外成本是否可以接受？

同时，能替代某家供应商，并不意味着能无条件替代它供应的每一种零部件。落到真实采购时，还需要核实具体物料的规格、认证范围、到货时间，以及相关商务条件。

再看缓解措施的状态，它可以是“已提出”“已批准”“进行中”“已完成”或者“已取消”。这个状态定义，为后续工作流表达进度提供了基础。

正式接入业务时，可以先由系统辅助整理候选方案，再由有权限的人审批，之后交给采购或运营流程执行。当前页面展示的是这些对象和关系的定义。

我们希望形成的工作方式是：风险有依据，措施有条件，执行有责任人，结果可以复盘。

## 七、本体如何为 AI 提问提供业务上下文｜约 1.5 分钟

**屏幕操作：**在「自然语言查询（NL2ONTOLOGY）」输入 `查看 Component 的 daysOfSupplyOnHand 属性`，点击「运行查询」。可选补充问题：`查看本体结构`。多跳追溯使用前文的「路径查找」。

现在我们用一句话来提问：“查看零部件的库存缓冲天数属性。”

这里为了准确对应图中的名称，我使用了实体和属性的英文标识。系统会返回这个属性的定义：它是整数，单位是天，表示当前库存缓冲天数。

这个演示说明，本体可以为问题提供明确的业务上下文：问题里提到什么对象，关注哪个属性，以及这个属性的业务含义。刚才的路径查找，则展示了对象之间的连接方式。

当前页面使用本地规则演示问题与模型结构的对应关系。后续接入真实数据、查询服务和权限之后，才能进一步验证面向业务数据的自然语言问答。

对 AI 应用来说，这层业务定义的价值在于，让回答能够围绕企业确认过的对象和关系组织起来。我们也可以据此检查：回答是否找对了对象，路径是否合理，计算口径是否一致。

当然，本体的作用不止于 AI。数据分析、业务协同和跨系统集成，同样可以使用这套共同的业务定义。

## 八、结束：把演示转成一个可以验证的业务问题｜约 1.5 分钟

**屏幕操作：**回到完整图谱，点击「适应视图」。不要在收尾时临时切换未经准备的外部服务。

回到开场的三个问题：影响谁，还能撑多久，有哪些应对选择？

今天这张图，给出了组织这些问题的方式。通过对象，我们明确在讨论什么；通过属性，我们明确判断需要什么信息；通过关系，我们把分散在不同业务环节的信息连接起来；通过评估和措施，我们把分析与后续工作衔接起来。

如果结合贵司的业务，我建议先选一个具体场景，例如“一家关键供应商停供后，对某条产品线有什么影响”。

我们一起确认几个关键对象，找出采购、库存和生产数据的来源，再用一次真实历史事件核对：关联是否正确、信息是否足够、判断是否符合业务实际。

价值也可以从具体工作上衡量：确认影响范围需要多久，跨部门核对减少了多少往返，备选方案能否说明依据，以及预估和实际情况相差多少。目标应基于贵司现有流程共同确定。

最后想请各位帮我们选一个起点：在供应中断、库存短缺和交付异常中，哪一种最值得先用贵司的一次真实事件来验证？

## 演示者速查：供应链本体的核心知识

| 核心知识 | 给客户的一句话解释 | 本场景中的例子 |
| --- | --- | --- |
| 业务语义 | 让不同部门和系统对同一个业务概念有共同定义 | “库存可用天数”需要共同确认统计口径 |
| 实体类型与实例 | 先定义一类对象，再承载具体记录 | Supplier 是类型，某家具体供应商是实例 |
| 属性、类型与单位 | 明确分析需要哪些信息、信息如何表达 | 库存缓冲为整数、单位 days；金额示例单位为 USD |
| 唯一标识 | 明确说的是哪一个对象，并建立跨系统编码对应 | supplierId、componentId、eventId |
| 关系与基数 | 明确对象如何连接，以及允许怎样的一对多、多对多关联 | Component → usedIn → ProductLine 为多对多 |
| 路径与影响分析 | 沿业务关系组织追溯，结合实际数据判断影响 | DisruptionEvent → Supplier → Component → ProductLine |
| 评估与行动对象 | 让评估时间、置信度、候选措施和进度有结构可循 | RiskAssessment、MitigationAction |
| 模型、数据和规则的分工 | 本体定义含义与连接；真实结论还需要数据、计算和业务规则 | 定义 revenueAtRisk 字段不等于已经计算风险收入 |

### 七类实体与关键字段

| 业务对象 | 页面名称 | 重点字段 | 主要业务问题 |
| --- | --- | --- | --- |
| 供应商 | Supplier | supplierId、tier、reliabilityScore、singleSourced | 依赖谁，是否存在单一来源风险？ |
| 零部件 | Component | componentId、daysOfSupplyOnHand、leadTimeDays、criticalityLevel | 库存能支撑多久，补货需多久，缺料有多关键？ |
| 产品线 | ProductLine | productLineId、annualRevenue、productionStatus | 涉及哪些业务，当前生产状态是什么？ |
| 中断事件 | DisruptionEvent | eventId、type、severity、startDate、estimatedDurationDays、region | 发生了什么，预计持续多久？ |
| 风险评估 | RiskAssessment | assessmentId、assessedDate、revenueAtRisk、timeToImpactDays、confidenceLevel | 何时评估，预计影响是什么，有多大把握？ |
| 缓解措施 | MitigationAction | actionId、type、status、estimatedCost、leadTimeSavedDays | 有哪些行动，预计成本与时间收益如何？ |
| 备选供应商 | AlternativeSupplier | altSupplierId、qualificationStatus、capacityAvailable、pricePremiumPercent | 认证、产能与成本条件如何？ |

### 七条关系：以当前实际模型为准

| 起点 | 关系 | 终点 | 当前模型基数 |
| --- | --- | --- | --- |
| Supplier | supplies，供应 | Component | 一对多 |
| Component | usedIn，用于 | ProductLine | 多对多 |
| DisruptionEvent | affects，影响 | Supplier | 多对多 |
| DisruptionEvent | triggers，触发 | RiskAssessment | 一对多 |
| RiskAssessment | recommends，推荐 | MitigationAction | 一对多 |
| MitigationAction | activates，启用 | AlternativeSupplier | 多对多 |
| AlternativeSupplier | canReplace，可替代 | Supplier | 多对一 |

“触发”“推荐”“启用”在本页面中是关系名称，不能据此说明后台已自动执行这些动作。

## 客户常见问题与建议回答

**1. 这与我们已有的 ERP、报表是什么关系？**

ERP 等系统继续承载业务记录和流程。本体把跨系统需要共同理解的对象、属性、关系表达清楚，供分析或应用使用。具体采用哪些数据、如何接入，需要结合现有架构确认。

**2. 图画好了，AI 就能准确回答所有问题了吗？**

还需要真实数据、正确映射、计算口径、查询能力和访问权限。本体提供业务上下文，回答质量要用真实问题和已知结果验证。

**3. 当前系统能自动计算损失、切换供应商或下采购单吗？**

当前演示的是模型查看、属性和关系检查、路径查找，以及本地规则查询。风险计算和业务执行需要另外完成数据、规则、接口与权限集成，并经过业务验收。

**4. 为什么还要建风险评估和缓解措施，而不只建供应商、产品？**

因为我们还希望表达“什么时候做了什么判断，建议做什么，以及推进到什么状态”。评估和措施成为对象后，就有了结构化管理这些信息的基础；完整证据与责任记录仍需按业务补充。

**5. 如果我们关注仓储物流，不是供应商中断呢？**

同样的方法可以用于订单、发货、承运商、仓库和库存。项目中的「IQ 实验：零售供应链」提供了 15 类实体、18 条关系的另一套模型，其中订单明细表达某笔订单买某个产品的数量，库存对象连接产品与仓库。可按实际客户业务另选主线。

备课时需注意的模型简化：

1. `Supplier → Component` 当前标为一对多，但零部件说明提到可能来自多个供应商。若贵司同一物料存在多来源，需要重新确认供货关系基数，以及是否建立含价格、比例、有效期的供货关系对象。
2. `RiskAssessment` 没有直接连接具体产品线、零部件或证据记录；`AlternativeSupplier` 也没有直接连接获准替代的具体物料。正文仅讲已有结构。逐产品线评估或物料级替代，需要扩展关系与数据。
3. `singleSourced` 在本模型中定义为“没有已获批准的替代来源”。不要同时把一个示例描述成该字段为 true，又已有 Approved 且适用的替代来源；真实业务应确认这一标记的粒度和更新规则。
4. 本模型没有订单、客户、采购单、生产计划、审批人或执行接口。课程中的自动化时间线、风险金额、公式和效果目标均未作为本稿的系统能力或业务结论引用。
5. 当前枚举和单位是模型定义，不表示后台已经执行了数据校验、审批、预测或风险计算。路径可达也不等于已确认因果、实际影响或经济损失。
